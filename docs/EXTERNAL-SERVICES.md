Эта инструкция предназначена администратору, который уже располагает базой данных или системой учётных записей. Если устанавливаете всё с нуля, используйте [основную инструкцию](../INITIAL_DEPLOYMENT.md).

Сначала выберите вариант 2, 3 или 4 в [основной инструкции](../INITIAL_DEPLOYMENT.md#variants) и скопируйте соответствующую готовую пару файлов. Выберите режимы ниже до первого `docker compose up -d`. Переключать режимы уже установленного стенда этой процедурой нельзя.

<a id="section-1"></a>
## Подготовить файлы

Откройте `.env` и `infrastructure.json` текстовым редактором. В JSON сохраните два верхних раздела: `postgres` и `keycloak`. Замените только содержимое раздела внешней службы. Примеры ниже — содержимое отдельного раздела, не всего файла. Содержимое раздела устанавливаемой службы оставьте `{"mode":"managed"}`. Используйте пару файлов из `examples/` для выбранного варианта установки.


<a id="section-2"></a>
## Выбрать состав служб

Готовые примеры уже содержат правильный состав Compose. Следующий список нужен для проверки выбранного варианта, а не для повторной ручной настройки:

Выберите ровно один вариант **до первого запуска**:

1. **Вариант 1 — обе службы устанавливаются вместе с UnicNet:**
   `COMPOSE_FILE=compose.yml|compose.pg.yml|compose.keycloak.yml`. Обе секции JSON — `managed`. Подготовка внешних служб не требуется.
2. **Вариант 2 — внешний PostgreSQL, Keycloak устанавливается вместе с UnicNet:**
   `COMPOSE_FILE=compose.yml|compose.keycloak.yml`. В JSON секция `postgres` — `external`, секция `keycloak` — `managed`.
3. **Вариант 3 — PostgreSQL устанавливается вместе с UnicNet, внешний Keycloak:**
   `COMPOSE_FILE=compose.yml|compose.pg.yml`. В JSON секция `postgres` — `managed`, секция `keycloak` — `external`.
4. **Вариант 4 — обе службы уже существуют:**
   `COMPOSE_FILE=compose.yml`. Обе секции JSON — `external`.

Нумерация совпадает с [основной инструкцией](../INITIAL_DEPLOYMENT.md#variants).

`COMPOSE_PATH_SEPARATOR=|` оставьте без изменений. Символ `|` здесь записывается в файл `.env`, а не вводится отдельной командой терминала.

<a id="section-3"></a>
## Подключить внешний PostgreSQL

До установки получите у администратора постоянные адрес и порт PostgreSQL. Они должны оставаться доступными после перезапуска службы и сервера. Если PostgreSQL работает в Docker, администратор должен закрепить опубликованный порт; автоматически назначаемый случайный порт для постоянного подключения не подходит. В `infrastructure.json` укажите порт, доступный контейнерам UnicNet, а не обязательно внутренний порт контейнера PostgreSQL.

В `infrastructure.json` задайте соответствующий режим. Для внешнего PostgreSQL пример секции:

```json
{"mode":"external","host":"db.example.internal","port":5432,"database":"unicnet","username":"unicnet_owner","password":"YOUR_PASSWORD","sslmode":"verify-full"}
```

`localhost` внутри контейнера не подходит; для БД на Docker-хосте используйте `host.docker.internal`. Имя подключения должно соответствовать сертификату, если используется `verify-full`. Если встроенный Keycloak подключается к внешнему PostgreSQL, его таблицы тоже будут находиться в выделенной базе UnicNet.

<a id="database-owner"></a>
### Подготовить пустую базу и владельца

Эти действия выполняет администратор PostgreSQL до установки UnicNet. Нужна отдельная пустая база, которая не используется другими приложениями. Пример для новой базы: в административной сессии `psql` выполните по очереди:

```sql
CREATE ROLE unicnet_owner LOGIN;
\password unicnet_owner
CREATE DATABASE unicnet OWNER unicnet_owner;
```

Команда `\password` запрашивает пароль интерактивно; вводите его в терминале, не в тексте SQL. Имена базы и роли можно заменить согласованными значениями, а затем указать те же значения в `infrastructure.json`. Если база или роль уже существуют, не повторяйте создание: администратор должен проверить их назначение, владельца и отсутствие чужих данных. Установщик внешние базы и роли не создаёт.

Администратор PostgreSQL также должен:

- разрешить вход роли и создание объектов в выделенной базе, включая необходимые схемы;
- настроить адрес прослушивания, TLS, правила `pg_hba.conf` и сетевой доступ со стороны контейнеров UnicNet;
- передать адрес, постоянный порт, имя базы, пользователя, пароль и сведения о доверии сертификату;
- проверить подключение с выбранным `sslmode` из согласованного окружения контейнеров, а не только с самого сервера БД.

Порядок работы с сертификатами и границы проверенной конфигурации приведены [ниже](#certificates).

<a id="section-4"></a>
## Подключить внешний Keycloak

Получите у администратора постоянный URL Keycloak, доступный контейнерам UnicNet и пользователям. Адрес и порт должны сохраняться после перезапуска службы. Подготовка внешних PostgreSQL и Keycloak выполняется их администратором до запуска установки UnicNet.

Для внешнего Keycloak:

```json
{"mode":"external","url":"https://sso.example.internal","realm_mode":"existing","realm":"unicnet","client":"FrontUiV2","admin_username":"unicnet-service","admin_password":"SET_SECRET_BEFORE_USE","login_username":"existing-admin","login_password":"SET_SECRET_BEFORE_USE"}
```

Realm — область пользователей, клиентов и прав в Keycloak. Client — зарегистрированное в ней приложение. Для UnicNet по умолчанию используется клиент `FrontUiV2`. Названия в примере можно заменить, сохранив согласованность с настройками Keycloak.

<a id="service-account"></a>
### Подготовить служебную запись

Действия выполняет администратор Keycloak. Текущая интеграция получает токен через **`master/admin-cli`** с именем и паролем пользователя. Пользователь только в realm приложения и клиент с включённым **Service accounts** не заменяют эту запись.

1. В административной консоли выберите realm **master**.
2. В **Users** создайте отдельного пользователя `unicnet-service`, включите его и задайте постоянный пароль в **Credentials**. Не оставляйте незавершённые **Required actions**. Эту запись используют приложения, а не сотрудники для повседневного входа.
3. Проверьте, что политика Keycloak разрешает этой записи получение токена по паролю через клиент `admin-cli`. Если политика организации запрещает такой способ входа, текущую интеграцию необходимо согласовать с поставщиком до запуска.
4. Назначьте права согласно выбранному режиму ниже. В `infrastructure.json` внесите имя и пароль этой записи в `admin_username` и `admin_password`.

Глобальная роль `admin` в `master` даёт управление всеми realms. Не назначайте её как обычный способ подключения к существующему общему SSO. Права целевого realm назначаются пользователю `master` через клиент **`ИМЯ_REALM-realm`** в **Role mapping → Assign role → Filter by clients**. Это отличается от клиента `realm-management` внутри самого целевого realm.

Для управления пользователями и настройками UnicNet используйте роли клиента целевого realm: `view-realm`, `manage-realm`, `view-clients`, `manage-clients`, `query-clients`, `view-users`, `manage-users`, `query-users`, `query-groups`, `query-realms`. Этот набор разрешает администрирование соответствующих ресурсов целевого realm; он не объявляется минимальным набором для каждого отдельного действия. Более узкие назначения и дополнительные ограничения организации требуют отдельной приёмки функций приложения.

Механизм делегирования описан в [официальном руководстве Keycloak 26.7](https://www.keycloak.org/docs/26.7.0/server_admin/index.html), раздел **Global and Realm specific roles**. Назначение ролей по документации Keycloak не заменяет проверку работы UnicNet с политиками вашего SSO.

<a id="new-realm"></a>
### Создать новый realm

1. Согласуйте новое уникальное имя realm, которое ещё не занято.
2. Администратор Keycloak назначает служебной записи realm role **`create-realm`** в `master`. Keycloak предоставляет создателю права на созданный им realm. Назначение через консоль и возможность отображать realms могут дополнительно потребовать `query-realms` согласно политике Keycloak.
3. В секции `keycloak` установите `realm_mode=create`, укажите новое имя в `realm` и клиент в `client`.
4. Удалите поля `login_username` и `login_password`: начального пользователя создаст установщик, его реквизиты будут в `initial-admin.json`.
5. После установки проверьте вход и создание персонального администратора. Согласуйте с администратором SSO отзыв права создания новых realms с сохранением прав на realm UnicNet; повторный запуск уже настроенного стенда не должен использовать глобальную роль `admin`.

Не создавайте пустой realm вручную перед этим режимом. Если имя уже занято realm, созданным вне данной установки, установщик откажется его перезаписывать. Для него нужен режим `existing`.

<a id="existing-realm"></a>
### Подключить существующий realm

Подготовьте выделенный для UnicNet realm. Установщик не дополняет произвольный чужой realm до рабочей конфигурации.

1. В выбранном realm создайте или проверьте включённый клиент **`FrontUiV2`** с протоколом **OpenID Connect**. В **Capability config** установите **Client authentication = Off**, включите **Direct access grants** и **Standard flow**. Это публичный клиент: поле client secret в JSON установки не требуется.
2. Для стандартного HTTP-пилота задайте **Valid redirect URIs** как `http://ВАШ_АДРЕС:8080/*`, **Web origins** как `http://ВАШ_АДРЕС:8080`. Подставьте значение `UNICNET_HOST`; для согласованного HTTPS используйте фактический адрес пользовательского интерфейса. Не используйте произвольное `*` для всех адресов.
3. Создайте realm roles `admin`, `superUser`, `user`. Создайте группу **Administrators**, назначьте ей realm role `admin`, атрибут `access_level=admin` и все атрибуты `_grants` со значением `write` из [справочника прав](README-FIRST-RUN.md#attributes).
4. Для настройки атрибутов пользователей разрешите в **Realm settings → User profile** политику **Unmanaged attributes = Admin can edit** (`unmanagedAttributePolicy=ADMIN_EDIT`). Не ослабляйте политику общего SSO без согласования его владельца; используйте отдельный realm UnicNet.
5. Создайте включённого проверочного пользователя, задайте пароль и включите его в **Administrators**. Завершите все обязательные действия до первого входа через UnicNet. Для этой проверки используется вход по имени и паролю; обязательная MFA в таком потоке требует отдельного согласования интеграции.
6. В `master` назначьте служебной записи права клиента этого realm по разделу [подготовки служебной записи](#service-account). Право `create-realm` для режима `existing` не требуется.
7. В `infrastructure.json` задайте `realm_mode=existing`, имя realm и клиента. В `login_username` и `login_password` внесите реквизиты проверочного пользователя приложения, а не служебной записи `master`.

После установки войдите проверочным пользователем и создайте персональных администраторов. В режиме `existing` используйте переданные вами login-реквизиты; сгенерированный пароль в `initial-admin.json` не заменяет пароль пользователя существующего realm.

Инициализатор не перенастраивает внешний `master` и не создаёт или удаляет его пользователей. Существующий realm не перезаписывается; при работе приложения могут обновляться настройки и записи пользователей в пределах выданных прав.

Режимы JSON и выбранные Compose-файлы должны совпадать; `prepare` проверяет это. Готовность клиента, полные права записи и весь UnicNet с внешними службами нужно принять на целевом стенде. Одноразовые задания входят в ту же сеть Compose, что и приложения.

<a id="certificates"></a>
## TLS и доверие сертификатам

До первого запуска администраторы внешних служб передают цепочку сертификатов, DNS-имена подключения и требования к проверке подлинности. Настройка доверия на Linux-хосте сама по себе не добавляет доверие внутри Docker-образов.

**PostgreSQL.** Пример JSON использует `sslmode=verify-full`: требуется доверие к издателю и совпадение имени подключения с сертификатом сервера. Инициализатор использует PostgreSQL-клиент, приложения — Npgsql, а встроенный Keycloak при внешней БД — JDBC. Доверие необходимо настроить для каждого из этих потребителей. Добавление файла только в один контейнер не обеспечивает работу всей установки. Механизмы описаны в [документации PostgreSQL](https://www.postgresql.org/docs/18/libpq-ssl.html), [Npgsql](https://www.npgsql.org/doc/security.html) и [PostgreSQL JDBC](https://jdbc.postgresql.org/documentation/ssl/).

**Keycloak.** Для `https://` сертификат должен быть действующим, соответствовать имени URL и быть доверенным одновременно инициализатору и приложениям. Сервер Keycloak должен отдавать необходимую цепочку промежуточных сертификатов. HTTP-подключение в изолированном пилоте и подключение с проверкой HTTPS — разные условия приёмки.

**Граница текущей поставки.** Штатные Compose-файлы не содержат подключения произвольных корпоративных CA, клиентских сертификатов и закрытых ключей. В JSON нет поля, которое автоматически устанавливает такой сертификат во все образы. Если для выбранной инфраструктуры требуется дополнительное доверие, до запуска получите у поставщика согласованные файлы подключения сертификатов и проверку именно с вашими PostgreSQL/Keycloak. Эта часть не является готовой процедурой установки в текущем репозитории.

Четыре варианта установки приняты с TLS `require` для внешнего PostgreSQL и HTTP для внешнего Keycloak. Это не подтверждает `verify-full`, HTTPS или работу с минимальными делегированными правами: в проверке использовалась административная служебная запись. Режим `require` шифрует соединение, но сам по себе не подтверждает подлинность сервера для всех используемых клиентов. Не заменяйте согласованный `verify-full` на `require` или `disable` для обхода ошибки сертификата; для пилота режим проверки должен быть выбран явно и согласован до установки.


<a id="section-5"></a>
## Продолжение установки

Сохраните оба файла. Проверьте доступность внешних служб именно с Docker-сервера и из контейнерной сети. Не используйте адрес `localhost` для удалённой службы: внутри контейнера он означает сам контейнер.

Вернитесь к разделам [запуска](../INITIAL_DEPLOYMENT.md#start) и [проверки результата](../INITIAL_DEPLOYMENT.md#login): выполните вход в registry, проверку конфигурации, скачивание, запуск и проверку результата. При одной внешней службе ожидаются четыре успешно завершённых задания и семь healthy-служб; при двух — четыре задания и шесть healthy-служб.

Внешний Keycloak открывается по вашему существующему адресу, а не обязательно на порту 8095. В режиме `existing` для входа в UnicNet используйте указанного вами пользователя `login_username` и его пароль. Его роль и разрешения должны соответствовать [справочнику пользователей](README-FIRST-RUN.md).

Состав файлов и границы поставки приведены в [описании поставки](DEPLOYMENT-DETAILS.md). Подключения с TLS и ограниченными делегированными правами необходимо проверить в вашей инфраструктуре.
