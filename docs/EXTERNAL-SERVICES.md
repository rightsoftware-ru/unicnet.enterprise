Сначала выберите вариант 2, 3 или 4 в [основной инструкции](../INITIAL_DEPLOYMENT.md#variants) и скопируйте соответствующую готовую пару файлов. Выберите режимы ниже до первого `docker compose up -d`. Переключать режимы уже установленного стенда этой процедурой нельзя.

<a id="section-1"></a>
## Подготовить файлы

Откройте `.env` и `infrastructure.json` текстовым редактором. В JSON сохраните два верхних раздела: `postgres` и `keycloak`. Замените только содержимое раздела внешней службы. Примеры ниже — содержимое отдельного раздела, не всего файла. Содержимое раздела устанавливаемой службы оставьте `{"mode":"managed"}`. Используйте пару файлов из `examples/` для выбранного варианта установки.


<a id="section-2"></a>
## Выбрать состав служб

Готовые примеры уже содержат правильный состав Compose. Следующий список нужен для проверки выбранного варианта, а не для повторной ручной настройки:

Выберите ровно один вариант **до первого запуска**:

1. **Внешний PostgreSQL, Keycloak устанавливается вместе с UnicNet:**
   `COMPOSE_FILE=compose.yml|compose.keycloak.yml`. В JSON секция `postgres` — `external`, секция `keycloak` — `managed`.
2. **PostgreSQL устанавливается вместе с UnicNet, внешний Keycloak:**
   `COMPOSE_FILE=compose.yml|compose.pg.yml`. В JSON секция `postgres` — `managed`, секция `keycloak` — `external`.
3. **Обе службы уже существуют:**
   `COMPOSE_FILE=compose.yml`. Обе секции JSON — `external`.

Стандартный вариант с установкой обеих служб: `COMPOSE_FILE=compose.yml|compose.pg.yml|compose.keycloak.yml`, обе секции — `managed`.

`COMPOSE_PATH_SEPARATOR=|` оставьте без изменений. Символ `|` здесь записывается в файл `.env`, а не вводится отдельной командой терминала.

<a id="section-3"></a>
## Подключить внешний PostgreSQL

До установки получите у администратора постоянные адрес и порт PostgreSQL. Они должны оставаться доступными после перезапуска службы и сервера. Если PostgreSQL работает в Docker, администратор должен закрепить опубликованный порт; автоматически назначаемый случайный порт для постоянного подключения не подходит. В `infrastructure.json` укажите порт, доступный контейнерам UnicNet, а не обязательно внутренний порт контейнера PostgreSQL.

В `infrastructure.json` задайте соответствующий режим. Для внешнего PostgreSQL пример секции:

```json
{"mode":"external","host":"db.example.internal","port":5432,"database":"unicnet","username":"unicnet_owner","password":"YOUR_PASSWORD","sslmode":"verify-full"}
```

Это **отдельная пустая база**, пользователь — её владелец. `localhost` внутри контейнера не подходит; для БД на Docker-хосте используйте `host.docker.internal`. Администратор PostgreSQL заранее создаёт базу и отдельную роль-владельца с правом подключения и создания объектов в этой базе. Установщик внешние базы и роли не создаёт. Доступность порта, DNS и настройки pg_hba.conf проверяются со стороны контейнерной сети. Для verify-full необходимы проверка имени сервера и доверенный сертификат; способ передачи цепочки доверия в используемые образы согласуйте с поставщиком. Не отключайте TLS для обхода ошибки сертификата. Если Keycloak managed, его таблицы тоже будут в этой выделенной базе.

<a id="section-4"></a>
## Подключить внешний Keycloak

Получите у администратора постоянный URL Keycloak, доступный контейнерам UnicNet и пользователям. Адрес и порт должны сохраняться после перезапуска службы. Подготовка внешних PostgreSQL и Keycloak выполняется их администратором до запуска установки UnicNet.

Для внешнего Keycloak:

```json
{"mode":"external","url":"https://sso.example.internal","realm_mode":"existing","realm":"unicnet","client":"FrontUiV2","admin_username":"unicnet-service","admin_password":"SET_SECRET_BEFORE_USE","login_username":"existing-admin","login_password":"SET_SECRET_BEFORE_USE"}
```

Служебная запись должна существовать и иметь делегированные права целевого realm; текущий клиент получает её токен через master/admin-cli. Готовый realm должен содержать нужный клиент с Direct Access Grants и пользователя Admin с атрибутами доступа UnicNet. Realm — отдельная область пользователей и клиентов Keycloak. Client — зарегистрированное в ней приложение; по умолчанию используется `FrontUiV2`. Режим `existing` проверяет готовый realm, клиент и вход указанного пользователя.

Для нового realm задайте `realm_mode=create` и уберите `login_username` и `login_password`; дополнительно потребуется право его создания. Существующий чужой realm не перезаписывается. Внешний master не перенастраивается, его пользователи не создаются/не удаляются.

Режимы JSON и выбранные Compose-файлы должны совпадать; `prepare` проверяет это. Готовность клиента, полные права записи и весь UnicNet с внешними службами нужно принять на целевом стенде. Одноразовые задания входят в ту же сеть Compose, что и приложения.


<a id="section-5"></a>
## Продолжение установки

Сохраните оба файла. Проверьте доступность внешних служб именно с Docker-сервера и из контейнерной сети. Не используйте адрес `localhost` для удалённой службы: внутри контейнера он означает сам контейнер.

Вернитесь к разделам [запуска](../INITIAL_DEPLOYMENT.md#start) и [проверки результата](../INITIAL_DEPLOYMENT.md#login): выполните вход в registry, проверку конфигурации, скачивание, запуск и проверку результата. При одной внешней службе ожидаются четыре успешно завершённых задания и семь healthy-служб; при двух — четыре задания и шесть healthy-служб.

Внешний Keycloak открывается по вашему существующему адресу, а не обязательно на порту 8095. В режиме `existing` для входа в UnicNet используйте указанного вами пользователя `login_username` и его пароль. Его роль и разрешения должны соответствовать [справочнику пользователей](README-FIRST-RUN.md).

Состав файлов и границы поставки приведены в [описании поставки](DEPLOYMENT-DETAILS.md). Подключения с TLS и ограниченными делегированными правами необходимо проверить в вашей инфраструктуре.
