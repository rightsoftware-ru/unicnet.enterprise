## Сетевые доступы и порты

Перед установкой согласуйте правила межсетевого экрана. Команды установки не создают правила firewall и не устанавливают TLS-сертификаты.

Входящие порты, опубликованные Compose на Docker-хосте:

- TCP 8080 — Frontend, доступ пользователей к приложению.
- TCP 8095 — консоль и API встроенного Keycloak; отсутствует при внешнем Keycloak.
- TCP 30111 — Backend, TCP 30115 — Router, TCP 8082 — Logger, TCP 8001 — HTTP API SysLog. Предоставляйте доступ только согласованным источникам.
- UDP 514, TCP и UDP 601, TCP 6514 — опубликованные порты SysLog для устройств. Наличие порта 6514 само по себе не подтверждает настройку TLS-приёма; параметры приёма согласуйте отдельно.
- TCP 8200 — Vault, опубликован только на loopback Docker-хоста (127.0.0.1), для локальной диагностики.

По умолчанию остальные опубликованные порты привязаны ко всем интерфейсам хоста. Внутренним API не требуется доступ из Интернета; ограничьте доступ средствами сетевого периметра и правилами, учитывающими публикацию Docker-портов. Compose не содержит обратного прокси и не настраивает HTTPS для пользовательского интерфейса. Для промышленного HTTPS используйте согласованный с поставщиком внешний прокси и процедуру настройки адресов до первого запуска.

Исходящие соединения:

- HTTPS к cr.yandex и адресам загрузки, используемым registry, для скачивания образов.
- DNS и доступ к используемым внешним PostgreSQL и Keycloak. PostgreSQL обычно использует TCP 5432, но применяется порт, указанный администратором. Keycloak использует порт его URL.
- Доступ Router к устройствам по протоколам управления вашей инфраструктуры. Конкретный набор протоколов и портов определяется настроенными задачами и устройствами; один UNICNET_CIDR не заменяет правила доступа.

Встроенный PostgreSQL не публикует порт на Docker-хосте. Между контейнерами используются DNS-имена служб и внутренние порты Docker-сети. Адрес localhost внутри контейнера обозначает сам контейнер.

<a id="diagnostics"></a>
## Проверка состояния и журналы

Команды выполняются из исходной папки установки под учётной записью, имеющей доступ к Docker:

```sh
docker compose ps -a
docker compose logs --tail 20 verify
```

Четыре задания prepare/database/init/verify должны завершиться с кодом 0. Остальные выбранные службы должны быть healthy. Наличие контейнера в состоянии Up само по себе не подтверждает успешную инициализацию: требуются успешный verify и проверка первого входа из основной инструкции.

Для диагностики конкретной службы используйте её имя, например:

```sh
docker compose logs --tail 100 backend
docker compose logs --tail 100 init
```

Запрашивайте pg и keycloak только в вариантах со встроенной соответствующей службой. Docker logs выводит сообщения контейнеров; прикладные журналы также могут сохраняться в PostgreSQL через Logger. Политику хранения данных и ротацию журналов Docker задаёт администратор. Автоматическая очистка журналов этой поставкой не настраивается.

<a id="restart"></a>
## Остановка и запуск

Остановить проект с сохранением данных:

```sh
docker compose stop
```

Повторно запустить:

```sh
docker compose up -d
```

Приложениям выделено 40 секунд на штатное завершение. После повторного запуска проверьте состояния и verify. Не меняйте папку конфигурации или имя проекта, чтобы случайно не создать новый набор volumes.

<a id="data"></a>
## Данные и резервное копирование

Сохранять необходимо согласованный набор данных: PostgreSQL, состояние и секреты инициализатора в volumes, ключи и настройки приложений, frontend-settings.json, рабочую конфигурацию и лицензию. При внешнем Keycloak его база и настройки резервируются владельцем этой службы; при встроенном Keycloak его данные находятся в выделенной базе PostgreSQL.

Получить имена volumes проекта можно без вывода паролей:

```sh
docker compose config --volumes
```

Политика копирования, шифрования резервных копий, сроки хранения и проверка восстановления должны быть согласованы до промышленной эксплуатации. Рабочая процедура автоматического резервного копирования и восстановления в эту поставку не включена. Копия одного compose.yml не является резервной копией установленной системы.

Не используйте docker compose down -v, docker volume prune и ручное удаление volumes для устранения ошибки установки: это может удалить необходимые данные. Изменение базы, realm, адресов и лицензии после инициализации требует отдельной процедуры поставщика. Обновление заменой тега образа этим руководством не описывается.

<a id="credentials"></a>
## Реквизиты и передача диагностики

Рабочие .env, infrastructure.json, license.txt, initial-admin.json и frontend-settings.json не должны попадать в Git, переписку или заявки поддержки. Доступ к каталогу установки и Docker предоставляйте только администраторам. Файлы, управляемые контейнерами, могут иметь владельца с числовым UID; не меняйте их владельца и права произвольно.

Создайте персональные административные записи и проверьте их до отключения начальных admin. Служебную запись unicnet-service используют приложения; смена её пароля требует согласованного обновления реквизитов.

В заявку поддержки включайте версию поставки, выбранный вариант, команду с ошибкой, состояния контейнеров и обезличенный фрагмент журнала. Не передавайте полный вывод docker inspect или конфигурацию окружения: они могут содержать пароли и лицензию. При случайной публикации секрет нужно отозвать или сменить; удаление файла или коммита само по себе не отменяет утечку.

<a id="release"></a>
## Версия поставки для поддержки

Для обращения в поддержку сохраните идентификатор коммита, а при установке из архива — имя полученного архива. Установленные образы можно посмотреть из папки установки:

```sh
docker compose images
```

Если файлы получены через Git, дополнительно запишите идентификатор текущего коммита:

```sh
git rev-parse --short HEAD
```

Для установки из архива команда Git не требуется. Одного тега образа недостаточно для определения версии файлов установки: одинаковый тег может использоваться при разных редакциях Compose и документации.

Направляйте обращение через канал поддержки, согласованный с представителем поставщика при получении лицензии. Включите идентификатор коммита или имя архива, номер варианта 1–4, версии Docker/Compose, шаг инструкции и результат проверки. Прикладывайте только необходимые обезличенные строки журнала. Адрес поддержки и сроки ответа определяются условиями вашего пилота; общедоступный контакт в этой поставке не указан.
