# Техническое устройство развёртывания

Для установки используйте [пошаговую инструкцию](../README.md). Ниже — сведения для сопровождения и разработки.

## Порядок запуска


1. `prepare` проверяет файл лицензии, создаёт случайные пароли/ключи в `init-state` и отдельные файлы окружения в volumes каждого сервиса. Готовит импорт realm и права файлов Frontend.
2. `pg` запускается; `database` проверяет выделенную базу и создаёт маркер принадлежности до того, как туда начнут писать Vault/Keycloak. Для внешнего PostgreSQL база должна быть отдельной и пустой.
3. `keycloak` запускается с новым realm. Его локальная подготовка HTTP выполняется внутри его контейнера. При последующих стартах используется постоянная служебная запись.
4. `vault` запускается с `Vault__Bootstrap__Enabled=false`. Контейнер настройки подписывает сервисные JWT тем же способом, который уже используют клиенты UnicNet. Публичная выдача bootstrap-токенов не включается ни на одном этапе.
5. `init` создаёт постоянных администраторов/служебную запись Keycloak, удаляет временного bootstrap-пользователя, записывает настройки Vault и проверяет каждое значение.
6. После успешного `init` запускаются Logger, Router, SysLog, Backend и Frontend; затем `verify` проверяет готовность.

Лицензия передаётся в окружение каждого .NET-процесса под именем `UniCommLicenseData` до вызова его Main. Существующая первая проверка лицензии в сервисах сохраняется.

Docker socket и доступ к Docker API служебным контейнерам не предоставляются. Общий приватный журнал видят только служебные контейнеры. Каждый сервис получает собственный volume с окружением. Не публикуйте `init-state` и файлы окружения: там секреты.


## Версии и хранение данных

Поставка использует приложения и unicnetinit с тегом rc-init-test, PostgreSQL 18 и Keycloak 26.7.0. Манифест образов находится в корне репозитория. По умолчанию имя проекта — unicnet-docker-test; его изменение создаст другой набор volumes.

После успешной инициализации начальная конфигурация и лицензия закреплены. Смена адресов, лицензии, базы или realm требует отдельной процедуры. Повторный запуск проверяет настроенный стенд, сохраняя ключи и рабочие настройки.

## Необязательная сборка инициализатора

Обычная установка получает готовый образ из registry. Следующие команды предназначены только разработчикам и выполняются из корня репозитория; для сборки нужны доступ к Docker Hub и пакетным серверам Debian:

```sh
docker compose -f compose.yml -f compose.pg.yml -f compose.keycloak.yml -f compose.build.yml build prepare
```

Команда приведена для обеих управляемых служб. Для внешних служб исключите соответствующий файл compose.pg.yml или compose.keycloak.yml. Локальная сборка использует тег инициализатора из .env и может заменить локальный образ с этим тегом.

Исходники контейнерного инициализатора находятся в init/. Python на хосте нужен только для разработки и дополнительных тестов, описанных в [ACCEPTANCE.md](../ACCEPTANCE.md).
