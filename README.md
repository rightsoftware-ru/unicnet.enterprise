# UnicNet: установка через Docker Compose

Поставка для **нового стенда UnicNet**. На хосте нужны Docker Engine / Docker Desktop с Linux-контейнерами и Compose v2. Python и установочные скрипты на хосте не нужны. Служебная программа поставляется готовым образом unicnetinit из registry.

Образы приложений и инициализатора используют тег rc-init-test. Установка выполняется из корня репозитория командой Docker Compose; install.sh удалён. Процедура обновления/резервного копирования из v16 в Compose-вариант пока не перенесена. Простая замена тега не является проверенной процедурой обновления рабочего стенда.

## Первый запуск на Windows

Откройте терминал в корне репозитория. Для новой установки создайте локальные конфигурационные файлы из примеров. Не перезаписывайте файлы настроенного стенда:

```powershell
Copy-Item .env.example .env
Copy-Item infrastructure.example.json infrastructure.json
Copy-Item frontend-settings.example.json frontend-settings.json
```

Положите действующую лицензию:

```powershell
Copy-Item /path/to/deployment .\license.txt
```

Откройте `.env`. Укажите `UNICNET_HOST` — DNS или IPv4 сервера без протокола и порта — и `UNICNET_CIDR` — сеть устройств. `localhost` подходит для входа с самого Docker-хоста; для других рабочих мест укажите доступный адрес сервера. Остальные строки для первого опыта оставьте как есть.

```powershell
docker login cr.yandex
docker compose config --quiet
docker compose pull
docker compose up -d
docker compose logs --tail 20 verify
docker compose ps -a
```

Для установки достаточно доступа к Yandex Registry. Семь образов (шесть приложений и unicnetinit) загружаются под тегом `rc-init-test`. Пароли и JWT-ключи вручную задавать не нужно. Не запускайте одновременно старый стенд на тех же портах.

`docker compose wait verify` здесь не используется: установленный Compose не находит уже завершившийся verify и пишет no containers for project. Это само по себе не признак ошибки установки. Проверяйте ps -a и logs verify.

`prepare`, `database`, `init`, `verify` — одноразовые службы. Для них **Exited (0) — нормальный успешный результат**. Остальные контейнеры должны работать. `verify` проверяет HTTP, первый вход администратора и закрытый bootstrap Vault. Если он завершился с ненулевым кодом, установка не принята: смотрите логи.

Заберите реквизиты первого входа:

```powershell
docker compose cp prepare:/state/initial-admin.json .\initial-admin.json
```

Откройте файл локально. Для стандартного варианта вход в UnicNet — `http://АДРЕС:8080`, Keycloak — `http://АДРЕС:8095/admin/master/console/`. Начальные admin имеют случайный пароль; сервисы используют отдельную запись. После успешного `verify` создайте персональных администраторов. Перечень атрибутов пользователя — в [справочнике первого входа](docs/README-FIRST-RUN.md), раздел 5; служебные права разработки клиентским пользователям не выдаются.

На Linux используются те же команды Docker; файлы скопируйте через `cp`. Храните каталог и выгруженные реквизиты с доступом только для администраторов. Секретные файлы и логи с персональными данными не отправляйте в задачу.

## Что происходит внутри

1. `prepare` проверяет файл лицензии, создаёт случайные пароли/ключи в `init-state` и отдельные файлы окружения в volumes каждого сервиса. Готовит импорт realm и права файлов Frontend.
2. `pg` запускается; `database` проверяет выделенную базу и создаёт маркер принадлежности до того, как туда начнут писать Vault/Keycloak. Для внешнего PostgreSQL база должна быть отдельной и пустой.
3. `keycloak` запускается с новым realm. Его локальная подготовка HTTP выполняется внутри его контейнера. При последующих стартах используется постоянная служебная запись.
4. `vault` запускается с `Vault__Bootstrap__Enabled=false`. Контейнер настройки подписывает сервисные JWT тем же способом, который уже используют клиенты UnicNet. Публичная выдача bootstrap-токенов не включается ни на одном этапе.
5. `init` создаёт постоянных администраторов/служебную запись Keycloak, удаляет временного bootstrap-пользователя, записывает настройки Vault и проверяет каждое значение.
6. После успешного `init` запускаются Logger, Router, SysLog, Backend и Frontend; затем `verify` проверяет готовность.

Лицензия передаётся в окружение каждого .NET-процесса под именем `UniCommLicenseData` до вызова его Main. Существующая первая проверка лицензии в сервисах сохраняется.

Docker socket и доступ к Docker API служебным контейнерам не предоставляются. Общий приватный журнал видят только служебные контейнеры. Каждый сервис получает собственный volume с окружением. Не публикуйте `init-state` и файлы окружения: там секреты.

## Ошибка и повторный запуск

```powershell
docker compose ps -a
docker compose logs --tail 100 prepare database keycloak vault init verify
```

Если ранняя подготовка не прошла, исправьте причину и повторите `docker compose up -d`. После исправления сетевой проблемы/прав внешней службы можно повторно запустить `init` через `docker compose up -d init`, затем запустить весь проект и дождаться `verify`.

Пароли и ключи при повторе сохраняются. После успешного наполнения Vault повторный `init` проверяет наличие обязательных настроек, не сбрасывает пользователей и не перезаписывает изменённые через UnicNet/Vault значения. Смена начального пароля после успешного `verify` не ломает повторный запуск.

После создания БД нельзя подменять её имя/владельца, JWT-ключи, realm или managed/external режим. После успешного `init` начальная конфигурация и лицензия закреплены: их изменение блокируется. Ротация лицензии/адресов и обновление приложений требуют отдельной процедуры, которую ещё предстоит перенести в контейнерный вариант.

Постоянные volumes имеют префикс `unicnet-docker-test_`. Старые `unicnet_*` автоматически не подключаются. Не выполняйте `down -v`, если хотите сохранить данные этого теста. `down` без `-v` останавливает проект с сохранением volumes.

## Если PostgreSQL или Keycloak уже есть

Используется механизм выбора файлов Compose, без изменения основного файла. В `.env` строка `COMPOSE_FILE` содержит разделённые `|` имена:

| Нужные службы | COMPOSE_FILE |
|---|---|
| Свои PostgreSQL и Keycloak | `compose.yml\|compose.pg.yml\|compose.keycloak.yml` |
| Внешний PostgreSQL, свой Keycloak | `compose.yml\|compose.keycloak.yml` |
| Свой PostgreSQL, внешний Keycloak | `compose.yml\|compose.pg.yml` |
| Обе службы внешние | `compose.yml` |

Символы `\|` в таблице обозначают обычные `|` в .env. `COMPOSE_PATH_SEPARATOR=|` оставьте: так одинаково работает на Windows и Linux.

В `infrastructure.json` задайте соответствующий режим. Для внешнего PostgreSQL пример секции:

```json
{"mode":"external","host":"db.example.internal","port":5432,"database":"unicnet","username":"unicnet_owner","password":"YOUR_PASSWORD","sslmode":"verify-full"}
```

Это **отдельная пустая база**, пользователь — её владелец. `localhost` внутри контейнера не подходит; для БД на Docker-хосте используйте `host.docker.internal`. Нужны сеть, права создания таблиц/схем и доверенный сертификат для verify-full. Если Keycloak managed, его таблицы тоже будут в этой выделенной базе.

Для внешнего Keycloak:

```json
{"mode":"external","url":"https://sso.example.internal","realm_mode":"existing","realm":"unicnet","client":"FrontUiV2","admin_username":"unicnet-service","admin_password":"SET_SECRET_BEFORE_USE","login_username":"existing-admin","login_password":"SET_SECRET_BEFORE_USE"}
```

Служебная запись должна существовать и иметь делегированные права целевого realm; текущий клиент получает её токен через master/admin-cli. Готовый realm должен содержать нужный клиент с Direct Access Grants и пользователя Admin с атрибутами доступа UnicNet. Для нового realm задайте `realm_mode=create` и уберите login-поля; дополнительно потребуется право его создания. Существующий чужой realm не перезаписывается. Внешний master не перенастраивается, его пользователи не создаются/не удаляются.

Режимы JSON и выбранные Compose-файлы должны совпадать; `prepare` проверяет это. Готовность клиента, полные права записи и весь UnicNet с внешними службами нужно принять на целевом стенде. Одноразовые задания входят в ту же сеть Compose, что и приложения.

## Граница проверки

Проверяются генерация/сохранение реквизитов, подпись JWT, отсутствие обращения к bootstrap API при наполнении, запрет повторной записи настроенного стенда и четыре графа Compose. Отдельный opt-in тест запускает временные PostgreSQL/Keycloak без приложений UnicNet, проверяет подготовку БД, создание администраторов, удаление bootstrap-пользователя и перезапуск Keycloak с постоянной служебной записью.

Изолированный тест не запускает приложения UnicNet. Отдельно на тестовом стенде подтверждены managed-запуск, HTTP readiness, первый вход и закрытый bootstrap. На 198.51.100.10 также проверены все три сочетания внешних служб, создание и использование готового realm, первый и повторный запуск. Результаты и ограничения тестовых внешних служб: [отчёт приёмки](docs/acceptance-results.json). Внешние службы заказчика требуют проверки их сети, TLS и делегированных прав.

## Необязательная сборка из исходников

Для разработчика: добавьте compose.build.yml к выбранному списку -f и выполните docker compose build prepare. Этот режим требует Docker Hub и пакетных серверов Debian; обычной установке он не нужен.

## Проверка развёртывания

На Linux выполните `sh accept-deployment.sh` после завершения `verify`. Результаты и ограничения приёмки описаны в [ACCEPTANCE.md](ACCEPTANCE.md). Исходники инициализатора находятся в `init/`; Python на сервере для обычной установки не требуется.
